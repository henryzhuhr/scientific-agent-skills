# Pull 请求文档模板

> **返回 [Markdown 样式指南](../markdown_style_guide.md)** — 首先阅读样式指南以了解格式、引用和表情符号规则。

* *使用此模板用于：** 将 Pull 请求记录为持久的、可搜索的 Markdown 记录。该文件是 PR，而不是配套文档。它捕获了所有内容：更改的内容、原因、如何验证、安全影响、部署策略以及学到的内容。

* *主要功能：**包含影响分类的摘要、之前/之后的变更清单、测试证据、安全审查、重大变更文档、部署策略、可观察性计划、回滚计划和审阅者清单。

* *理念：**此文件是 PR 描述 - 不是同伴，不是补充，不是副本。 GitHub PR 是一个细指针：人们去那里评论差异、批准和观看 CI。但实际记录——发生了什么变化、为什么发生变化、测试证据、回滚计划和吸取的教训——都在这里，并提交给存储库。

当有人问“PR #123 是关于什么的？”六个月后，他们将是 `grep docs/project/pr/`，而不是 GitHub API。当您从 GitHub 迁移到 GitLab 时，每条 PR 记录都会随之而来。当人工智能代理需要了解模块的历史记录时，它会在本地读取这些文件——没有令牌，没有速率限制，没有平台依赖性。

这就是 [Everything is Code](../markdown_style_guide.md#-everything-is-code)理念：项目管理数据存在于存储库中、版本化且可移植。不要在 GitHub UI 中捕获应在此文件中捕获的信息。投入10分钟。一份出色的公关文件可以消除“这个公关是关于什么的？”的问题。 Slack 消息和“有人可以检查 GitHub PR 吗？”上下文切换 — 答案已在存储库中。

```

docs/project/pr/pr-00000124-add-job-retry-metrics.md
docs/project/pr/pr-00000125-refactor-ci-stage-order.md
```

- **目录：** `docs/project/pr/`
- **命名：** `pr-` + PR 编号以零填充到 8 位 + `-` + 简短的小写连字符描述
- **交叉引用：** 链接到元数据表中的实时 PR
- **GitHub PR 主体：** 仅使用此文件的完整分支 URL（例如，`https://github.com/<org>/<repo>/blob/<branch>/docs/project/pr/pr-00000123-fix-auth-timeout.md`）
